# 게임 기획서

문서 상태: 초기 설계안. 사용자 요구사항은 **확정 요구사항**, 추가 설계는 **제안**, 아직 정하지 않은 정책은 **미정**으로 구분한다. 예시 고유명사·대사·수치는 정식 콘텐츠가 아니다.

관련 문서: [기술 및 데이터 설계](TECH_STACK.md), [개발 계획](IMPLEMENTATION_PLAN.md), [개발 규칙](../AGENTS.md).

## 1. 게임의 핵심 — 확정 요구사항

중세 판타지 세계에서 플레이어는 외신 니알라토텝의 사도가 되어, 일반적인 교회로 위장한 이단 교회를 운영한다. 방문자의 고민과 기억에 개입해 그들을 신도로 만드는 것이 목표다.

게임의 중심은 교단 규모나 자원 관리가 아니라 **개별 캐릭터와의 반복적인 만남, 고해성사, 사고 편집으로 변화하는 개인 서사**다. 비주얼노벨, 미연시 스타일 캐릭터 공략, 심리 호러, 텍스트 편집 퍼즐을 결합한다. 캐릭터 공략이 연애 관계를 필수로 의미하는지는 미정이다.

브라우저에서 실행하는 싱글플레이 게임이며 React·TypeScript 기반으로 개발한다. 초기 저장은 localStorage를 사용하고 백엔드, 계정, 데이터베이스, AI API, Unity, Phaser는 사용하지 않는다.

## 2. 플레이 경험

### 확정된 기본 순환

1. 캐릭터와 만나 대화한다.
2. 고해성사를 통해 고민, 과거, 기억, 비밀을 알아낸다.
3. 캐릭터의 정신에 진입해 사전에 지정된 텍스트를 편집한다.
4. 편집 결과를 확정한다.
5. 변화한 상태와 기억이 이후 대화, 행동, 개인 루트에 반영된다.

### 연출 제안

- 일상적인 고해성사의 차분한 화면에서 사고 편집에 진입할 때 글자 간격, 배경 명암, 문장 배치가 변한다.
- 호러는 편집 전후의 말투와 기억의 모순을 통해 전달한다. 강한 점멸이나 점프 스케어를 기본 전제로 삼지 않는다.
- 방문자의 믿음을 바꾸는 행위가 항상 안정적인 결과를 주지는 않도록 설계할 수 있다. 구체적인 실패·대가 체계는 미정이다.

## 3. 시스템

### 3.1 고해성사

캐릭터 초상화·스탠딩 이미지, 배경, 화자, 대사창, 선택지, 대화 분기, 상태별 대사, 대화 로그를 제공한다. 고해성사는 대화 엔진을 공유하되 화면 연출과 현재 장면 종류로 일반 대화와 구분하는 방식을 제안한다.

선택과 노드 진입 효과는 데이터로 정의한다. 이미 지나간 로그는 당시 표시된 대사를 기록하며, 이후 상태가 바뀌었다고 과거 대사를 다시 계산하지 않는 방식을 제안한다.

### 3.2 사고 편집

확정 기능은 **삭제**와 **치환**이다. 초기에는 자유 입력을 허용하지 않는다. 지정된 단어·문장 영역만 선택하고, 치환은 제공된 대체 단어 중에서 고른다. 편집 가능한 영역은 화면상 명확히 구분한다.

다음 절차를 제안한다.

1. 현재 장면의 텍스트와 편집 가능 영역을 표시한다.
2. 영역을 선택하고 허용된 편집 기능을 선택한다.
3. 원문과 변경된 문장을 비교한다. 이때 실제 캐릭터 상태는 바꾸지 않는다.
4. 확정 시 유효성을 다시 확인하고 상태·플래그·기록·진행 위치를 함께 변경한다.
5. 결과 확인 화면을 거쳐 후속 대화로 돌아간다.

프로토타입은 한 세션에서 편집 **한 건**을 확정하는 방식을 제안한다. 사용자가 확정한 것은 '한 번의 사고 편집으로 변화를 확인하는 흐름'이며, 세부 편집 건수 제한은 구현 전 결정한다. 확정 전 선택 취소·변경은 허용하는 방식을 권장한다. 무편집 통과, 세션 이탈, 확정 후 되돌리기, 편집 비용과 실패 확률은 미정이다.

확장 시 단어 이동, 문장 연결, 문장 삽입을 명시적인 편집 연산으로 추가한다. 초기 버전에 해당 기능의 UI나 실제 처리 코드를 선행 구현하지 않는다.

### 3.3 캐릭터 상태

| 상태 | 의미 | 해석 시 주의점 |
| --- | --- | --- |
| 친밀도 `affinity` | 플레이어에 대한 개인적 유대 | 신앙과 별개다. |
| 신앙도 `faith` | 니알라토텝 또는 교리에 대한 믿음 | 교회에 대한 호감과 같다고 가정하지 않는다. |
| 의심도 `suspicion` | 교회·플레이어·상황에 대한 의심 | 높은 수치의 결과는 루트별로 정의한다. |
| 자아 균열도 `egoFracture` | 기억·자기 인식의 불안정성 | 무조건적인 공략 진척으로 취급하지 않는다. |

각 캐릭터는 사고 편집 기록, 기억 변화 플래그, 이벤트 진행 상태, 개인 루트 진행도, 확인한 엔딩도 별도로 가진다. 수치 범위, 초기값, 증감 공식과 플레이어에게 보여 줄 정보 범위는 미정이다. 기술 문서의 0~100 범위와 초기값은 검증 가능한 데이터 예시를 위한 제안이다.

### 3.4 개인 루트와 엔딩

캐릭터마다 독립적인 진행 위치와 루트 상태를 갖는다. 이후 만남에서는 해당 캐릭터의 이전 선택·편집 기록에서 비롯된 상태와 플래그를 조건으로 대사와 이벤트를 결정한다.

엔딩의 개수·이름·정식 조건·정사 여부는 미정이다. 프로토타입은 삭제와 치환의 결과를 서로 다른 후속 대사와 임시 엔딩으로 보여 주는 방식을 제안한다. 신앙 수치만으로 엔딩을 결정해야 한다는 규칙은 없다.

## 4. 화면과 시각 방향

PC 가로형 16:9 구성을 기준으로 한다. 고딕 판타지, 종교적 신비주의, 심리 호러를 표현하되 현재는 플레이스홀더 이미지와 임시 스타일만 사용한다.

| 화면 | 주요 요소 | 다음 흐름 |
| --- | --- | --- |
| 타이틀 | 제목, 새 게임, 이어하기 | 교회 내부 |
| 교회 내부·대화 | 배경, 캐릭터, 화자, 대사, 선택지, 로그 | 고해성사 |
| 고해성사 | 대화 UI, 고해성사 장면 표시 | 사고 편집 |
| 사고 편집 | 원문, 선택 가능한 영역, 삭제·치환, 미리보기, 확정 | 결과 확인 |
| 결과 확인 | 바뀐 문장, 결과 설명 | 후속 대화 |

후속 대화 종료 후에는 대화 화면에 엔딩 요약과 타이틀 복귀를 제공하는 구성을 제안한다. 별도의 여섯 번째 전체 화면을 필수로 추가하지 않는다.

레이아웃은 배경·캐릭터 레이어와 대화 UI를 분리한다. 16:9 외 화면에서는 중앙 정렬과 여백을 사용하고, 작은 화면에서는 대사창과 선택지가 잘리지 않도록 확장한다. 키보드 조작, 명확한 포커스, 텍스트 대비, 연출 감소 설정 지원을 제안한다. 구체적인 브라우저 지원 범위와 모바일 최적화 수준은 미정이다.

## 5. 최초 프로토타입 범위

### 포함 — 확정 요구사항

- 캐릭터 한 명, 짧은 개인 서사.
- 시작 → 등장 → 대화 → 고해성사 → 사고 편집 → 치환 또는 삭제 → 확정 → 결과 확인 → 후속 대화와 변화한 결말.
- 네 종류의 상태값과 기억 플래그, 편집 기록.
- JSON 시나리오와 컴포넌트·게임 로직의 분리.
- 플레이스홀더 비주얼, localStorage 저장·복원.

### 이번 프로토타입에서 제외

여러 캐릭터의 실제 콘텐츠, 교단 경영, 장기 일정·경제 시스템, 자유 텍스트 입력, AI 생성 대사, 온라인 기능, 정식 일러스트. 미래 기능을 지원할 데이터 경계는 설계하되 해당 기능 자체는 만들지 않는다.

### 검증용 서사 제안

임시 방문자 '엘린'은 과거 사건을 자기 탓으로 받아들이고 있다. 내면 문장은 '그날의 잘못은 나의 탓이다.'다. `나의`를 `운명의`로 치환하면 책임을 외부로 돌리고, `나의 ` 영역을 삭제하면 책임의 주체가 흐려진다. 두 결과는 서로 다른 기억 플래그를 설정하고 후속 대사·임시 엔딩으로 이어진다.

이는 데이터 구조를 설명하는 샘플이다. 이름, 성별, 과거 사건, 대사, 수치 효과와 엔딩을 정식 설정으로 확정하지 않는다.

## 6. 결정이 필요한 사항

| 항목 | 제안 | 결정 시점 |
| --- | --- | --- |
| 작품 제목·주인공 설정·첫 캐릭터 | 임시 이름으로 구조부터 검증 | 콘텐츠 작성 전 |
| 상태 범위·초기값 | 0~100, 범위 밖 증감은 제한 | 상태 시스템 구현 전 |
| 편집 횟수 | 최초 세션은 한 건, 확정 전 변경 가능 | 편집 시스템 구현 전 |
| 무편집 통과·실패·비용·되돌리기 | 초기 구현에서 불필요한 규칙을 추가하지 않음 | 편집 시스템 구현 전 |
| 결과 표시 | 원문/수정문은 표시, 수치 공개 정도는 별도 결정 | 결과 UI 구현 전 |
| 저장 시점·슬롯 | 단일 자동 저장, 확정된 상태만 저장 | 저장 시스템 구현 전 |
| 복수 엔딩 조건 충돌 | 데이터의 명시적 순서와 기본 경로 사용 | 분기 시스템 구현 전 |
| 호러 강도·연애 요소·대상 연령 | 서사 방향을 별도 합의 | 정식 콘텐츠 작성 전 |
| 지원 브라우저·모바일·음향 | PC 우선, 음향은 별도 범위로 관리 | UI 검수 전 |

결정 전에는 위 항목을 확정 규칙으로 코드에 숨겨 넣지 않는다. 독립적인 문서·데이터 구조 작업은 계속 진행할 수 있다.
